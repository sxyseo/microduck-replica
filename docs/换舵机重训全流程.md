# 换舵机 / 换零件 → 调整 → 重训 → 部署 → 验证：全流程手册

> 回答一组连环问题：换了舵机厂家（或其他零件）后，**要改哪些东西？怎么重训 9 个 ONNX？
> 怎么测试（是否先测一只舵机）？树莓派和官方主板分别怎么用？整体思路是什么？**
> 事实基线：上游 `29e887e`；标签：`【已验证】`源码/本机实验核实 ｜ `【推断】`待实测 ｜ `【未完成】`未验证

---

## 0. 一张图看懂改动传播链

```
换舵机（硬件改动）
  ├─① 机械层   → 打印件舵机仓/孔位/MJCF 几何（外形变了才要改）
  ├─② 电气层   → 供电电压窗口 / 电流 / 接口线序
  ├─③ 通信层   → 协议（Dynamixel V2 / 飞特 / 宇树私有）+ 波特率 + ID 空间
  └─④ 动力学层 → 力矩/速度/回差/摩擦/PD 特性 —— 这层决定策略能不能直接用
                        │
        ②③④ 全部汇入 ▼
   MJCF 执行器模型（BAM 参数 + 域随机化范围）       ←── 单舵机台架辨识提供数据
                        │
                        ▼
   重训策略（9 个任务各自一次训练）──产出──▶ 9 个新 ONNX
                        │
                        ▼
   部署（官方 Rust 运行时 / 树莓派）──▶ 测试金字塔逐级验证
```

**总原则：改动是逐层传导的，上一层没锁死就别动下一层。** 每层的"改不改"由判定表决定（§1）。

## 1. 换舵机影响面判定表（先做这张表，再动手）

| 层 | 关键问题 | 若不兼容要改什么 |
|---|---|---|
| **① 几何** | 外形/安装孔/输出轴与 XL330（20×34×26，M2）一致吗 | 打印件舵机仓重画 + MJCF 网格替换 + 质量惯量重算 |
| **② 电气** | 电压窗口覆盖 6.6–8.2V（官方超压工况）？堵转电流 HAT/UBEC 供得起吗 | 供电架构（电池节数/UBEC/HAT 取舍）重做 |
| **③ 通信** | 协议是 Dynamixel V2？1Mbps？ID 空间够 16 台？回延迟寄存器存在吗 | 运行时写新控制器（飞特走 rustypot 现成模块）；`imu_to_dxl` 固件改协议分支（双协议设计已备） |
| **④ 动力学** | 力矩≥0.5N·m 量级、速度、回差、摩擦特性接近 | **执行器模型重辨识 + 策略必须重训**（官方 ONNX 作废） |

> 四层全兼容才谈得上"不改模型直接用"——当前市场没有这样的便宜货（见[执行器选型](执行器选型.md)）。
> 所以现实路径必然是：**逐层适配 + 重训**。本手册就是这条路的作业指导书。

## 2. 第一步永远是：单舵机台架测试（对，先测一只）

买 1–2 只新舵机，15 只大单之前把下面做完。工具：FE-URT-1 调试板（¥45，已在采购清单）+ USB 转 TTL + 可调电源。

### 2.1 电气与通信（半天）

| 测试 | 方法 | 通过标准 |
|---|---|---|
| 协议连通 | 调试板按其协议发 PING/读寄存器 | 能 ping 通、能写读位置 |
| 波特率 | 1Mbps 下收发 1000 包无 CRC 错 | 误包率 ≈0 |
| 电压窗口 | 6.6V / 7.4V / 8.2V 各跑 10 分钟 | 无过热保护、行为一致 |
| 堵转电流 | 堵转 2 秒读电流（电源显示） | 峰值 < 供电预算（15 只同启是大头） |

### 2.2 动力学辨识（一天，重训数据全从这来）

| 测什么 | 怎么测 | 进哪个参数 |
|---|---|---|
| **PD 阶跃响应** | 给位置阶跃（如 30°），示波/高频回读画出响应曲线 | `kp / kd`（BAM 的 stiffness/damping） |
| **堵转力矩-速度曲线** | 逐速度点堵转读力矩（带力矩反馈的舵机可直接读） | `forcerange`、力矩上限 |
| **回差** | 从正反两方向趋近同一目标位，读差值 | `backlash` 模型（mjlab 有 `backlash.py` 现成框架） |
| **摩擦** | 匀速转动测维持力矩 | `friction_base / friction_viscous` |
| **转子反射惯量** | 空载加减速拟合 | `armature` |

> 这一步的产出是一组 **BAM 参数**（对照 `robot/microduck/constants.py` 里官方那组）。
> 官方的参数也是这么测出来的（`joints_properties.xml` 里 5 组实测标定）——复刻者做一样的事。

## 3. 改仿真模型（全部在 `microduck_rl` 仓库内）

| 改什么 | 文件 | 说明 |
|---|---|---|
| 执行器参数 | `src/mjlab_microduck/actuator/friction_dr_bam.py` 配置 + `robot/microduck_constants.py` | 用 §2.2 的辨识值替换官方 BAM 参数；**注意 vin_range 按新舵机额定改**（官方是 6.5–8.2 超压特例，勿照抄） |
| 回差建模 | `tasks/backlash.py`（框架现成） | 填新舵机实测回差角 |
| 域随机化范围 | `tasks/microduck_velocity_env_cfg.py` L28–53 | 新舵机出厂差异大 → 范围放大；个体一致 → 可收窄。**范围 = 你的台架实测离散度** |
| 几何（仅当外形变了） | `robot/microduck/assets/` 网格 + 打印件 | 质量惯量随新网格重算；打印件连锁修改 |
| **不动的** | obs 61 维 / action 14 维 / reward 结构 / 课程表 | 关节还是那 14 个，接口规格不变（运行时省大改） |

验证改对了没有：跑 5 迭代冒烟，确认 obs/action 维度不变、无 NaN、reward 量级正常——再进训练。

## 4. 重训 9 个 ONNX：方法与优先级

### 4.1 先分清 9 个策略是什么

9 个 ONNX = **9 个技能，各自独立训练一次**（同一套配方，不同任务配置），每个仅 ~775 KiB：

| 官方策略 | 对应任务（`uv run list-envs` 里的 ID） | 优先级 |
|---|---|---|
| `alpha_walking` | `Mjlab-Velocity-Flat-MicroDuck` | ⭐ **第一个训**（核心技能） |
| `alpha_stand` | VelStand / SitStand 系 | ⭐ 第二（站立是安全兜底） |
| `alpha_sitstand` | `Mjlab-SitStand-Flat-MicroDuck` | 与站立可并行 |
| `alpha_ground_pick` | `Mjlab-GroundPick-Flat-MicroDuck` | 按需 |
| `ball_kick_left / right` | `Mjlab-BallKick-Flat-MicroDuck`（左右脚两次训练） | 按需 |
| `roller` / `roller_crouch` | `Mjlab-Velocity-Flat-MicroDuck-Rollers` / `RollerCrouch` | 做轮滑才训 |
| `roulade` | `Mjlab-Roulade-Flat-MicroDuck` | 玩乐技能最后 |

> 映射关系标注：任务↔策略文件名的对应为**推断**（依据任务语义与命名），以导出产物与运行时清单最终核对为准。

### 4.2 训练方法（三档算力）

| 档 | 命令 | 量级 | 用途 |
|---|---|---|---|
| 调试档（本机 CPU） | `CUDA_VISIBLE_DEVICES="" uv run train <任务ID> --env.scene.num-envs 64 --agent.max_iterations 100` | 4 分钟/百迭代 | 验证改的模型能跑、曲线方向对 |
| **正式档（GPU）** | `uv run train <任务ID> --env.scene.num-envs 4096 --agent.max_iterations <数千~数万>` | 数小时~天/技能 | **出可部署的策略**；无卡用 `--hf-jobs`（官方内置） |
| 批量档 | 9 个任务逐个跑（或 HF Jobs 排队） | ×9 | 全家桶 |

判断"训够了"的信号（对每个技能）：`fell_over` 稳定低位、`error_vel` 平台化、`mean_std` 收敛到低位——
和官方曲线对比（wandb/文档若公开）或以回放行为为准。**训练量参考：官方配方上限是 4096 环境 × 5 万迭代；
走路通常在数千迭代、10⁷–10⁸ 步量级出现**（expC 续训正在实证 CPU 量级的下限）。

### 4.3 导出与校验

- 训练目录自动生成 `.onnx`；**每次导出后跑一遍校验**：`rl-series/scripts/inspect_onnx.py` 确认 `obs[1,61] / actions[1,14]`；
- 9 个文件命名对齐运行时清单（`alpha_*` / `ball_kick_*` / `roller*` / `roulade`），放进更新包结构即可被 `updaterd` 分发。

## 5. 部署：树莓派 vs 官方主板（Radxa）

### 5.1 官方同款路线（Radxa Zero 3W）——零移植

- 软件（Armbian + Rust 运行时 + 设备树 overlay）原样跑：`deploy/` 脚本按官方流程走；
- **换舵机只影响 `duck-control/src/bus.rs` 以下的控制器层**：Dynamixel 兼容舵机 → 改 ID 表即可；
  飞特协议 → 换 rustypot 飞特模块（通信层现成）；宇树私有协议 → 写新控制器；
- 官方 HAT（已开源 Gerber）直接打样或按[总清单](复刻总清单.md)用转接板+UBEC 替代。

### 5.2 树莓派路线——两种用法

| 用法 | 做法 | 评价 |
|---|---|---|
| **地面调试台（推荐起步）** | 树莓派 + USB-TTL/FE-URT-1 接舵机，跑 rustypot/python 脚本做 §2 台架测试、批量写 ID/标定 | 零移植，第一天就能用 |
| **机载主控（要移植）** | 官方 HAT 物理上就是 Pi 40-pin HAT，可插 Pi 4/5；但要自己搞定：① UART 引脚复用 + 1Mbps（Pi 的 PL011 支持，需 dtoverlay 并关串口控制台）② i2c3→Pi 的 i2c 引脚映射 + TLV320AIC3104 音频 overlay ③ 摄像头 IMX219（Pi 原生支持 ✓）④ `duck-control` 交叉编译 aarch64 + 设备路径/实时优先级调整 ⑤ onnxruntime 用 Pi 的 aarch64 wheel（`duck_detect` 走 CPU ✓，RKNN 的 NPU 检测模型在 Pi 上不可用） | 可行，工作量 = 一次中型移植【推断，未验证】 |

> 结论：**官方主板路线是"改舵机"的最短路径**；树莓派先当调试台，机载化等走路跑通后再立项。
> 另注：官方 HAT 的 `imu_to_dxl`/音频依赖特定 i2c/i2s 控制器编号，Pi 上设备树要重写——这是移植工作量的主要来源。

## 6. 测试金字塔（新模型上线顺序，逐级收紧风险）

```
L1 单舵机台架        §2 —— 辨识数据本身（在买 15 只之前）
L2 仿真评估          新执行器模型下：旧策略跑 100 迭代评估 → 量化退化幅度（预期大，作为基线证据）
L3 重训后仿真评估    新策略回放（capture_rollout.py）+ 五指标曲线 —— 仿真内先"会走"
L4 总线联调          全部 15+1 台设备一次 sync_read 全回（duck-control 自检）
L5 吊装/悬空测试     策略上真机但整机吊起：验证关机序、限位、急停、无负载动作
L6 软垫地面遥控      跌落无损伤环境里试走；记录电流/温升/噪音
L7 平地验收          对照官方行为清单：站立→走→转→坐→拾取，逐技能验收
```

每级的**验证指标**：L3 用仿真五指标（reward/fell_over/误差/std）；L4 用误包率；L5–L7 用
"行为清单 + 电流/温度/机械噪声 + 视频留档"，全部回填[构建日志](../构建日志.md)的验证表。

## 7. 高频坑清单（每条都来自本仓库已发生的教训）

1. **换执行器后官方 ONNX 一定作废**——训练内嵌了执行器模型，"看起来差不多"不够；
2. **随机化范围是按官方舵机的离散度定的**，换舵机不重定范围 = 白随机；
3. **回差/摩擦实测数据比厂商标称可靠**——宇树 S288 的力矩标注风波就是前车之鉴；
4. obs 布局（61/76/14）是策略指纹，**动布局 = 三处同步改**（仿真/导出/运行时）+ 全部断言重跑；
5. 真机首跑永远先 L5 吊装——`robotd` 的 `safety.rs` 有保护，但物理世界没有 undo。
