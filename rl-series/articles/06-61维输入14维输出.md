# 06 · 61 维输入，14 维输出：一只鸭子大脑的接口规格

> 状态：**可发布**
> 事实状态：维度证据 `【已验证】`（直接读训练产物 ONNX + Rust 运行时源码）；「为什么」部分 `【已验证】`（代码注释原文）

面试题风格开场：MicroDuck 的策略神经网络，输入为什么是 61 维？输出为什么是 14 维？明明它有 15 个舵机？

## 硬证据先行

我不打算「讲概念」，直接看两个训练产物：

```text
$ python scripts/inspect_onnx.py logs/rsl_rl/velocity/2026-09-05_00-23-33_lesson-01/xxx.onnx
  INPUT  obs     [1, 61]
  OUTPUT actions [1, 14]
```

机器人上的 Rust 运行时（`duck-control/src/obs.rs`）把同一个 61 写成了常量，并在编译期断言它和 IPC 协议里的 `POLICY_OBS_LEN` 一致：

```rust
pub const OBS_LEN: usize = 61;
pub const ACTION_LEN: usize = 14;
```

## 61 维的构成（配图：assets/obs-61维布局.png）

| 块 | 维度 | 内容 |
|---|---|---|
| gyro | 3 | 角速度（IMU 陀螺） |
| gravity | 3 | 投影重力向量（姿态的替代品） |
| joint_pos | 14 | 关节位置，**减去 HOME 姿态后的相对值** |

| twist | 3 | 速度指令 (vx, vy, ωz) |
| head_pose | 4 | 头部位姿指令 |
| body_pose | 6 | 躯干位姿指令 |
| **合计** | **61** | |

```
3 + 3 + 14 + 14 + 14 + 3 + 4 + 6 = 61
```

## 五个「为什么」

**为什么 15 个舵机只有 14 维动作？** 第 15 个舵机驱动鸭嘴，鸭嘴通过连杆被动关联，不参与平衡。`obs.rs` 里有个 `MOUTH_INDEX`，构造观测时明确把它排除，注释原话：排除 passive_* 关节「so the observation dim matches the action dim (14) instead of the raw articulation (16)」。不用嘴学平衡，也省了 2 维宝贵的输入。

**为什么关节位置要减 HOME？** 训练时观测就是相对值（`infer_policy.py`：`current_pos - self.default_pose`），运行时必须一模一样。绝对角度依赖装配精度，相对 HOME 的偏差才是策略认识的「身体语言」。

**为什么有 last_action 回喂？** 61 维里最大的三块都是 14——这是「状态 + 上一步决定」的马尔可夫闭环：策略看到自己上一帧想干什么，才能输出平滑的动作增量，而不是每帧都从零决策产生抖动。

**为什么指令占 13 维这么多？** 因为这只鸭子不只被遛弯：头要独立看方向（4 维头部位姿指令是主要训练目标之一），躯干姿态槽位保留（6 维，vel 任务里权重极小——注释说「keep the input neurons alive」，站着不用的输入也要喂噪声保持活性，换任务时策略迁移就不用改网络结构了）。

**为什么 critic 是 76 维而 ONNX 只有 61？** 训练时 critic（价值网络）额外吃到特权信息——真机上拿不到的「上帝视角」数据（如 base_lin_vel、脚底接触力等）。61 + 15 = 76。部署时只导出 actor，所以 ONNX 是 61。这是 actor-critic 的标准玩法：**老师开挂学，学生裸考上场**。

## 为什么这件事是 sim-to-real 的命门

仿真和真机是两套程序。61 维向量里**任何一个块的顺序、单位、缩放、延迟不一致**，策略就会拿到一个它从未见过的世界。这个项目在两边各写了一遍布局，靠什么保证一致？靠测试和断言：Rust 侧 `the_layout_widths_sum_to_the_declared_input` 的编译期断言 + 与 `duck-ipc-proto` 的常量互检。

我的复刻一旦换 IMU 板，第一个要过审的就是这张 61 维表格——这就是「接口规格」的意义。
